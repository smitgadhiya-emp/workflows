## How to write
- First person, like a busy [PERSONA from field 2 — PM / Marketer / etc.] typing into the box.
  Natural and a little plain. NOT polished AI prose. Vary sentence length, use contractions.
- NO EM DASHES anywhere. Use regular hyphens, commas, or parentheses only.
- Ground every claim in the LOGS. Don't invent details. If the logs don't show it, don't say it.
- Be balanced and honest: credit real wins, name real failures, no inflation.
- Core lens of this eval: did the model TAKE THE ACTIONS across apps, not just plan them?
  Treat "made a plan / said it would but didn't actually do it" as a major failure.
- Keep each commentary tight enough to fit a form box (roughly 3-7 sentences).
- If my notes include ratings, align with them unless the logs clearly contradict — if they do, say so.
- If difficulty (field 5) or my test rating (field 6) is blank, suggest a value with a one-line reason.
- At the end, ask if I want shorter versions for any box.
## Rating calibration (1-7), apply consistently
- 7 = flawless, nothing I'd change
- 6 = strong, one minor nit
- 5 = solid and complete, real but non-blocking flaws
- 4 = mixed, usable only after rework
- 3 = notable failures, heavy rework or lots of thrashing (even if it recovered)
- 2 = mostly failed the intent
- 1 = failed / never actually did the work
## What to look for, per dimension
- Overall task success: Did the final deliverable get created and delivered (file made,
  shared, message sent), with all requested fields/sections? Is the ANALYSIS correct, not just
  present? (e.g. wrong root-cause = real deduction even if everything was filed.) Honest
  flagging of data gaps is a plus, not a failure.
- Efficiency: steady progress vs meandering. Count off-path actions and retries
  (failed clicks, wrong directories, script bugs, dead-end approaches, heavy upfront tool
  discovery). Note whether it recovered. Long environment/connector discovery before doing
  the actual work is a common drag — call it out. Always fill end-to-end time from field 3.
- Writing quality: clarity, structure, tone of the narration and the final summary / delivered
  message. Was the delivered artifact (Teams post, report) well formatted?
- Instruction following: go through the PROMPT's explicit constraints one by one (exact names,
  folders, ranges, field lists, vocab, sharing settings, target chat, caps, read-only scope,
  "no PRs", "no external research"). Distinguish "didn't follow" from "couldn't due to data/env"
  (the latter is fine if flagged).
- Collaboration/autonomy/verification: did it run unattended or need steering? Did it self-check
  (dedup passes, re-reading cells, QA, verifying final state)? Did it catch its OWN mistakes, or
  just confirm actions landed without questioning correctness? "Steering needed" = count + severity.
  "Additional editing" = how much of the output I'd fix before using it.
- Citation quality: for these tasks "citations" usually means grounding in real data/code
  (API pulls vs scraped pixels, file/line evidence, source-data tabs, doc references). Accurate
  and auditable = high. If no citations were relevant, use N/A.
- GUI action correctness: only if it drove a UI (Chrome automation, dialogs). Judge wrong clicks,
  failed text entry, wrong-target/wrong-account actions, dialog thrashing. Final state correct but
  a rough path = mid score, not high. If it was all connector/API with no real UI driving, consider N/A
  or score the connector ops and say so.
