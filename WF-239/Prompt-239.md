Our CORS setup is spread across three places that do not talk to each other, and I have stopped trusting any of them. There is cors() middleware in the Express services, there are hand-set headers on the Next.js API routes, and there is an Nginx layer in front adding its own headers on top. Every one of those can allow or block an origin, and when they disagree the one that actually wins is not the one anybody thinks. I want the real effective policy per route worked out, and I want the gaps between what we meant to allow and what we actually allow written down. I want the hard version of this. If two engineers ran this on the same commit and the same logs they should land on the same route list, the same effective policies, the same gap classifications, and the same ranking. If your output isn't reproducible, it's wrong.

Start from the repo sahidempiricinfotech-dotcom/cors-audit on branch main. The Express services are under services/, the Next.js app is under web/, and the Nginx configs are under infra/nginx/. Pull the CORS config out of all three layers. In Express that is the cors() middleware and anything setting Access-Control headers by hand, applied globally, per router, or inside a single handler. In Next.js it is headers set in route handlers, in next.config.js headers(), and in middleware.ts. In Nginx it is add_header Access-Control-* and any map or if blocks that drive them, across every server and location block including the includes. Read the whole chain, not the first file that looks like CORS.

Here is the first thing that makes this hard, and where a shallow pass will hand me a confident wrong answer. The effective policy on a route is not what any single layer says, it is what survives all of them stacked in request order. Nginx sits in front, so an add_header there can add to or shadow what the app sent, and Nginx add_header has its own inheritance rule where a location block that sets any add_header drops all the ones inherited from the server block, which silently changes CORS on that path. Inside Express, a global cors() runs before a route-level one, and a handler that writes Access-Control-Allow-Origin by hand overrides the middleware for that route. So for every route you have to resolve the layers in the order a real request hits them and state the effective policy that actually reaches the browser, then show your work by listing what each layer contributed and which layer won each header. If you cannot fully resolve the order for a route, say so and mark it, do not average the layers into a guess.

Then classify the gaps. Cross-reference the effective allowed-origin list per route against the real origins in the "CORS Request Logs" Google Sheet, Requests tab, in the Drive folder Engineering / CORS Audit, over the window 2026-06-15 through 2026-07-14 inclusive, IST, joined on route path and method. Four gap types, and be exact about each. A dead whitelist entry is an origin allowed in config that never appears in the logs for any route in the window, and it matters because a stale allowed origin is a domain someone could grab and abuse, so list each dead origin and everywhere it is still allowed. A silently blocked origin is one that shows up in the logs hitting a route but is not in that route's effective allow list, which means real users are getting CORS failures nobody logged as a bug, so tie it to the route and the request count. A wildcard on an authenticated route is any route whose effective policy is Access-Control-Allow-Origin * while the route also handles authenticated or credentialed requests, and note that a wildcard combined with allow-credentials is not just loose, most browsers reject it outright, so those routes are broken as well as unsafe. And a split-config override is any route where a global policy is quietly loosened by a route-level or handler-level or location-level setting, so the effective policy is more permissive than the global one meant to apply, which is the exact failure the global policy was supposed to prevent.

While you are resolving each route, check the preflight too. For any route that takes something other than a simple GET or POST, verify the OPTIONS preflight actually returns an Access-Control-Allow-Methods list, and that the list matches the methods the route really implements. Flag both directions: a method the handler implements but preflight does not advertise (real requests will fail after the preflight) and a method advertised but not implemented (the policy is lying about the surface). If a route needs preflight and has no OPTIONS handling at all, that is its own flag.

Now score each route's exposure out of 100 so the ranking holds still between runs. Use these numbers exactly. Policy risk is 45 for a wildcard on a route that handles authenticated or credentialed traffic, 35 for a wildcard on any other route that appears in the logs, 25 for a split-config override that loosens the intended policy, 15 for a dead entry set that widens the allowed surface, and 10 for a preflight methods mismatch on its own. Data exposure is 25 if the route reads or writes user data, auth, or payment info, 15 if it drives business logic, and 5 if it only serves public or static content, judged from what the handler actually touches in the repo. Reach is 20 for a route present in the logs from three or more distinct origins, 12 from one or two origins, and 5 for a route with no log rows at all, which you flag traffic-unknown rather than dropping. Rank by total, and when two routes tie, take the higher policy risk first, then the higher traffic count, then route path and method A to Z, so the order never moves. If a scoring input is missing in the source, say not available and score the components you can, do not invent a number and do not let a missing field push a route off the list.
