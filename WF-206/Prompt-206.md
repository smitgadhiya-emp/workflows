Our Express API has grown to the point where nobody can tell me how much of our user input is actually validated. Every service went in at a different time, some routes got express-validator, some got Joi, a couple got Zod, one team used celebrate, and the uploads service just trusts multer. When someone asks "is this field validated" the honest answer right now is "probably, let me go read the code for an hour." Map the whole input surface and tell me exactly where the holes are. I want the hard version of this, not a surface pass. If two engineers ran this on the same commit they should land on the same input list, the same coverage verdicts, the same scores, and the same ranking. If your output isn't reproducible, it's wrong.

The run has to cover every user-reachable input in the repo sahidempiricinfotech-dotcom/express-input-audit on branch main, across services/api-gateway/, services/orders-api/, services/uploads-api/, services/admin-api/ and shared/middleware/, and it ends in a coverage map, Jira tickets, and a Teams summary. An input means one field, so req.body.email is one input and req.body.address.zip is another. Find every place a handler touches req.body, req.params, req.query or req.headers, and treat the four as separate surfaces because they get validated very differently and headers almost never get validated at all. For each input record the route method and path, the mounted path (not just the path in the router file), the source file and line, the handler function name, and the field path.

Here is the first hard part, and it is where a lazy scan will quietly lie to me. You cannot just grep for req.body. Handlers alias it, so const { body } = req and const { email, qty } = req.body and a bare req passed into a service function that reads body two files away are all real access and all have to be counted. Follow the aliases and follow req into helper and service functions to find where the fields actually get read. If a handler spreads req.body straight into something like a model create or a query object, that is every field the client sent, not a known list, so record it as an unbounded object input rather than pretending you know the fields. When you genuinely cannot resolve what a handler reads, say so with your best candidate and a confidence level (high / medium / low) instead of guessing a field list.

Second hard part, working out what validation actually applies to a route. Middleware is inherited, so a route can be covered by something declared in router.use() in the same file, or app.use() several files up in the gateway, or a shared chain exported from shared/middleware/, and reading the route line on its own will report a false negative every time. Resolve the full middleware chain that runs before each handler, in order, including anything mounted above it, and only then decide what is validated. Order matters too, so validation that is registered after the handler in the chain does not count as coverage, and neither does an error handler. If a schema is built at runtime rather than written as a literal, reason out the field list from the code that builds it and mark that route medium confidence at best.

Third hard part, and this is the pattern I actually care about most. Coverage is per field, not per route. A route with express-validator on it looks green in every tool we have tried, but if the chain checks 3 fields and the handler reads 7, then 4 fields are wide open and the middleware is basically camouflage. So compare the exact field set the validator covers against the exact field set the handler reads, and report per field: validated, unvalidated, or validated-but-weak. Weak means the field is named in the schema but only its presence or type is checked while the handler uses it somewhere that needs more, so a Joi string() on a field that gets concatenated into a query, or a Zod field with no length bound that lands in a regex, or an express-validator exists() and nothing else. A route counts as a coverage gap when it has validation middleware and at least one unvalidated or weak field, and I want those called out separately from routes with no validation at all, because the gap routes are the dangerous ones. Nobody audits a route they think is covered.

The uploads path needs its own attention. For every multer route, check whether the file's MIME type, size and filename are validated before anything reads them, meaning fileFilter and limits are configured on the multer instance itself and not just checked inside the handler after the file already landed. Flag any route where the handler touches file.originalname, file.mimetype or file.path before those checks run, including filename used to build a path on disk. Unbounded filename handling with no length or pattern bound is the shape behind the Express ReDoS CVE that came out in May 2026, so treat it as a gap even when a size limit exists, and say which of MIME, size and filename is missing rather than just "not validated."

Score every unvalidated and weak input for exploitability out of 100, and use these numbers exactly so the ranking is reproducible. Reachability comes from the auth column in the "Route Traffic Data" Google Sheet in the Drive folder Engineering / Input Validation, and it is 40 for a public or unauthenticated route, 25 for any logged-in user, 10 for admin only. Sink severity is 30 if the value reaches a database query, a shell call, a filesystem path or a template, 15 if it drives business logic like a price or a quantity or a status, 5 if it is only logged or echoed back. Field shape is 20 for a file or an unbounded object or array, 12 for a string, 5 for a number or boolean. Traffic is 10 at 1000 or more requests per hour, 6 between 100 and 999, and 2 under 100. Use the traffic window 2026-06-15 through 2026-07-14 inclusive, IST, and join on method plus mounted path. If a route has no row in that sheet, give it 2 for traffic and flag it traffic-unknown, do not drop it and do not invent a number. Rank by total score, and when two inputs tie, take the higher traffic first, then public before authenticated, then route path and field name A to Z, so the order never moves between runs.
