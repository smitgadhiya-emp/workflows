Finding the actions is the first place this goes wrong, so do not just grep for a "use server" line at the top of a file. The directive works two ways and they have different blast radii. A file-level "use server" turns every exported async function in that file into a callable endpoint, including the helper someone exported only so a test could reach it, and that helper is now a public POST that nobody thinks of as an action. An inline "use server" inside a function body makes only that one closure an action, and those hide inside Client Components and inside functions that get passed down as props, so a file-level scan misses them entirely. Find both kinds. Then for the file-level ones, check every single export in the file rather than the two that obviously look like actions, because the unintended exports are the whole point of this audit.

Second, and this is the misconception I want caught rather than repeated. Auth has to be inside the action itself. A check in middleware.ts does not reliably protect a Server Action, because the matcher often does not cover the POST the action arrives on, and a check in the page or the layout that renders the form does not run at all when the action is invoked directly. So if the only thing standing between an attacker and a mutation is middleware or a layout, that action is unguarded, and I want it reported as unguarded with a note saying where the false comfort was coming from. Do not credit a guard just because it exists somewhere upstream in the render tree.

Third, look at where the guard sits relative to the work. An action that queries or mutates first and checks the session afterwards is not guarded, it is just polite, so the check has to run before any business logic or database call. And the guard has to actually stop execution, so an if that logs and falls through, or one that returns a value the caller ignores, is not a guard either. Read what happens after the check fails, do not just pattern match on getServerSession() being present in the file.

Fourth, separate authentication from authorization, because conflating them is how this stays broken. A session check tells you somebody is logged in and nothing more. If the action does something privileged, like changing a role, touching billing, or acting on another user's record, then it also needs a role check, and it needs an ownership check when the record id comes in through the action arguments. Action arguments are attacker controlled, so an action that verifies the session and then trusts the id it was handed is an IDOR and I want it scored as one. Give each action a verdict of guarded, unguarded, or partially-guarded, and when it is partial, say which of the three is missing (role check, ownership check, or guard ordering) rather than leaving it as "weak."

While you are in there, check CSRF posture too, which for Server Actions means the Origin and Host comparison Next does by default. Read next.config.js and flag anything that widens it, particularly entries under serverActions.allowedOrigins, and flag any custom middleware that rewrites or strips the Origin header before the action sees it. If the config is default and untouched, say that plainly rather than leaving the column empty.

Now classify what each action can actually reach, because an unguarded action that writes a payment record is a different animal from an unguarded one that reads a public config, and treating them the same is what makes these audits useless. Trace what the action reads and writes through to the concrete data model, following it into any helper or repository it calls rather than stopping at the first function boundary, and record the model names and whether the access is a read or a write. If an action takes a dynamic model or table name, record it as unbounded rather than picking one, and mark it medium confidence at best.
