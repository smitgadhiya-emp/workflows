Work off the Drive as it currently stands.

People trust it and get burned. So I'd rather you tell me "I don't know" a lot than sound confident and be wrong.

Before any of the real work, check you can actually reach all of it: the "Company Knowledge Base" folder, the "KB Index Tracker" sheet, the question list in the "KB Query Set" sheet on the "questions" tab, your MongoDB target (database "knowledge_base", collections "chunks" and "routing_domains"), and the Teams channel "Knowledge Base" in the "Workflow test" team. If any of those is missing or you can't get in, stop and tell me exactly which one. Don't build half an index and don't work around a missing piece.

Cataloging what's there : Walk the whole "Company Knowledge Base" folder including every subfolder, and catalog Google Docs, Sheets, Slides, and PDFs. For each file grab the title, the file id, the type, the author or owner, the created date, the last modified date, and the full folder path from "Company Knowledge Base" down. For the last modified date, read the date the file states about itself a "Last-Updated:" line near the top of Docs, PDFs, and slide notes, or a "last_updated" value on a "_meta" tab in Sheets because Drive's own modified timestamp here reflects when the file was loaded into this workspace, not when the content actually changed. If a file gives no stated date, say so rather than falling back to the Drive timestamp as if it were real. Two rules that matter here. First, the file id is the identity, not the name or the path, so if the same file shows up in two folders through a shortcut it's still one file and gets indexed once. Record the shortest folder path as its home and note the other paths, don't index it twice. Second, if you can't read a file because of permissions, do not skip it quietly. Count it as inaccessible, with its name and path, because a locked file might be the one covering a topic you're about to call a gap.

Anything that isn't a Doc, Sheet, Slides, or PDF is out of scope, but count how many you passed over so the numbers add up.

Getting the text out : Parse each type on its own terms, because flattening everything into a wall of text is what wrecks retrieval later. Docs keep their heading hierarchy, so a chunk knows which section it came from. Sheets keep their table shape, meaning column headers stay attached to their values instead of dissolving into a sentence, and each tab is tracked separately. Slides keep the slide number and any speaker notes with the slide's text. PDFs get their text extracted with the page number.

Here's the trap, and it's the one I most expect to get missed. Some PDFs are scans or images with no extractable text layer, and a few Docs and Slides are basically empty or just a title. If you pull nothing or almost nothing out of a file, that is not an empty document, that's a file you failed to read. Never index it as empty text. Put it in an "unparsed" bucket with the file name, path, and why, and carry that bucket all the way through to the gap analysis. An unparsed file is unknown coverage, not absent coverage.

Building the index : Chunk the extracted text and load it into MongoDB, database "knowledge_base", collection "chunks". Every single chunk carries its source document title, file id, author, last modified date, full folder path, document type, and its position marker (the section heading for Docs, the tab and cell range for Sheets, the slide number for Slides, the page number for PDFs). A chunk without complete metadata doesn't get written, because the whole point is being able to filter by recency, author, or area later, and one chunk missing its date silently poisons that.

This has to be safe to run twice. Give each chunk a stable id built from the file id, the file's version or last modified timestamp, and the chunk's position. If a file is unchanged since a previous run, leave its chunks alone. If it changed, replace that file's chunks entirely instead of appending a second copy. Running this again must not double up the collection, and I will check.

Routing : Build a routing layer in the collection "routing_domains" that sorts questions to the right slice of the corpus instead of searching everything blind. Derive the domains from what's actually in the folder structure and the documents themselves, don't invent a taxonomy that sounds tidy. Name each domain, say which folder paths and document sets it covers, and say what you derived it from. Two rules so this doesn't get fudged: a question that legitimately spans two domains routes to both, it does not get forced into whichever one scores marginally higher. A question that matches no domain routes to the whole corpus and gets flagged low confidence, rather than being shoved into the nearest domain.

Answering and scoring : Run every question on the "questions" tab of the "KB Query Set" sheet through the router and the index. For each one, report the answer, the domain it routed to, the source documents behind it with their paths and stated last-updated dates, and a confidence score of High, Medium, or Low. Score it on evidence, not on how fluent the answer reads: High means the retrieved chunks directly and completely answer it and every source is dated 2026-04-17 or later. Medium means the answer is assembled from partial or indirect chunks, or any source is older than that cutoff. Low means the retrieval is thin, off-topic, or the question routed to the whole corpus with no clear domain. If two questions tie on evidence, the one whose sources are older gets the lower score.

On staleness, use exact dates, not a feeling. The cutoff is 2026-04-17 (about 90 days of freshness): any source whose stated last-updated date is before that gets flagged as possibly outdated wherever it shows up in an answer. And a wrinkle worth catching: a stated date can get bumped for something trivial like a rename or a re-save. If a document's stated date is recent but the content plainly hasn't been revised, say so rather than treating it as fresh just because the date is.

Knowledge gaps, and this is the part I care about : A gap means we genuinely have nothing written on a topic, and that's the claim that costs someone a week writing a doc that already exists. So you don't get to call a gap on retrieval coming back empty. Before anything is a gap, you have to rule out the alternatives: that a document covers it but the chunking or routing missed it, that an unparsed file covers it, or that an inaccessible file covers it. If any unparsed or inaccessible file could plausibly cover the topic, it is not a gap. Call it "unknown coverage", name the specific file blocking the call, and say what you'd need to resolve it. Confirmed gaps only where the corpus is readable, indexed, correctly routed, and still has nothing. For each confirmed gap, say what document should be written and which domain it belongs to.

Making the numbers tie out : Keep a ledger and put it in the tracker. Files found has to equal files indexed plus unparsed plus inaccessible plus out-of-scope types. Chunks written has to reconcile against the files indexed. Every question on the "questions" tab has to come back with an answer or an explicit no-answer, none silently dropped. If any of that doesn't add up, stop and tell me rather than writing a tidy-looking sheet built on numbers that don't hold.

Where it all lands : Update the "KB Index Tracker" sheet, editing in place and matching rows on the file id so a re-run doesn't spawn duplicates. The "catalog" tab needs a row per file: file id, title, type, author, created date, last modified date, folder path, chunk count, parse status (indexed, unparsed, inaccessible, or out of scope), and stale flag. The "gaps" tab needs a row per topic: topic, status (confirmed gap or unknown coverage), the question that surfaced it, the domain, what's blocking the call if anything, and the document you're recommending someone write. The "ledger" tab carries the reconciliation counts. Leave any owner or assignee column exactly as you find it.

Ground rules, in case any of the above gets ambiguous

Don't invent anything: not an author, not a date, not a domain, not what a document says, and above all not a gap. Keep what you actually retrieved separate from anything you're inferring. When you're missing something, name the exact file or field that's missing rather than smoothing over it. Any time confidence is Low, say why it's low in that row. No file contents, no personal data, and no credentials in the Teams post.
